# 捷途 T1J 仪表投屏 — 抓包结论与协议说明

车机：捷途 T1J / 德赛西威 SV 固件 / Chery-8155 / Android 11
屏幕：display 0 = 1920x1080 中控主屏，display 2 = 1920x720 仪表屏，display 5 = 桌面自己的虚拟屏
约束：全程不 root、不用 Shizuku、不用无障碍。下面每条结论后面都标了证据在哪个文件。

---

## 1. 三指手势怎么拿到

`system_server` 里的 `com.android.server.wm.CarSystemGesturesManager` 把手势直接广播出来：

```
action  = android.intent.action.car_system_gesture_mode
extras  = gesture(int), display(int), MotionEvent
接收权限 = 无
gesture 编码 = 手指数 * 100 + 方向（0左 1右 2下 3上 4捏合）
→ 300 = 三指左滑，301 = 三指右滑
```

普通应用 `registerReceiver` 就能收到，这是整个方案免特权的根基。

注意：这个 action 是受保护的，`adb shell am broadcast` 会被拒（`SecurityException`），只有真手指才触发。
证据：`抓包数据/证据-三指手势.txt`（`CarSystemGestures.CarGestureDetector(432): ACTION_DOWN count1 ...`，
count3 的行是真三指时才有）。

## 2. 仪表模式（数字/经典/导航/极简）走哪条命令

德赛私有总线 **VDBus**（`/system/framework/vdbus.jar`，两个原车 jar 已放在 `原车jar/`）：

```
service   = CAR_INFO        （com.desaysv.ivi.vds.carinfo/.service.CarInfoService，exported，permission=null）
eventId   = 327681          （MODULE_CAR_SETTING）
请求 Bundle = { "CMD_ID": int }              缺 CMD_ID 服务端直接抛 RuntimeException("cmdId is null")
响应 Bundle = { "CMD_ID": int, "VALUE": int[] }
cmdId 232 = 仪表模式
```

**仪表模式取值对照（这次纠正过，之前把 3 认成数字模式是错的）**

| 协议值 | 模式 |
|---|---|
| 1 | 数字模式 |
| 2 | 经典模式 |
| 3 | **导航模式** |
| 4 | 极简模式 |

依据两条硬证据：
1. 弹窗无障碍事件里文案顺序是 `[仪表模式, 数字模式, 经典模式, 导航模式, 极简模式, 亮度]`；
2. SystemUI 写入 `value:[4]` 时，它自己的埋点报的是 `attributeId:"InstrumentMode", attributeValue:"3"`
   —— 即 **协议值 = 选项下标 + 1**。

原车切模式的完整链路（`证据-仪表模式.txt` 里 02:01:51 那段）：

```
D/VDB-EXTRA-CarInfoProxy(1140): [sendItemValues] moduleID:327681, cmdID:232, value:[4]
I/VDConnector(1140):          [set](297)service=CAR_INFO; event=327681
D/VDS-CarInfo-CarInfoService(1493): [65:onSet] onSet: eventId = 327681 cmdId = 232 values = [4]
I/VDConnector(1493):          [set](297)service=VEHICLE_HAL; event=29987     ← 服务端转发给 MCU
I/CarInfoModel(1140):         下发指令并延迟回调相关数据, moduleId=327681, requestCmdId=232, values=[4], delayCount=10
D/VDS-CarInfo-CarInfoService(1493): [47:onGet] ... cmdId = 232 values = [4]  ← 回读确认
```

服务端 `CarInfoService.onSet` 反编译见 `反编译/carinfo.dump`（搜 `CarInfoService.onSet`）：
只读 `CMD_ID` 和 `VALUE` 两个 key，**没有任何 uid / 权限判断**，拿到就转 `CarInfoManager.sendItemValues` 发给 MCU。
客户端 `CarInfoProxy.sendItemValues` 反编译见 `反编译/extra.dump`，和本项目 `Vd.setTheme()` 逐字节一致。

另外：仪表模式**不在** Settings（global/secure/system）里，也**不在** prop 里。
`settings对比/` 是切模式前后的完整快照 diff，唯一变化的只有 `com.desaysv.status.bar.status`。
所以想读/写仪表模式，只有总线这一条路。

## 3. 桌面音乐卡片为什么显示不了自装音乐

桌面那张卡是 `com.desaysv.launcher.card.T1hMediaCard` + `MediaViewModel.currVDMediaInfo`，
数据同样走 VDBus，service = **MEDIA**（`com.desaysv.ivi.vds.media/.service.MediaService`，exported，permission=null）：

```
393217  CURRENT_SOURCE_TYPE
393218  MEDIA_SOURCE_INFO      ← 卡片标题就是这个事件
393219  MEDIA_SOURCE_PLAY_LIST
393220  MEDIA_SOURCE_PLAY_STATUS   （抓包里最活跃，118 次）
393221  MEDIA_SOURCE_PLAY_TIME
393222  MEDIA_SOURCE_EXT_INFO
393236/393237  列表项 / 卡片播放状态
payload = Bundle.putParcelable("info", VDMediaInfo)
```

`VDMediaInfo` 的公开字段：`title artist album mediaType infoType collectStatus albumBuffer albumImgUrl
lyrics genre composer fileName fileUrl id programType extras`。

关键点在 `MediaType` 枚举：`UNKNOWN=1 LOCAL_MUSIC=2 FM=9 AM=10 ONLINE_MUSIC=14 QQ_MUSIC=23
NETEASE=25 CARPLAY=18 HICAR=19 UNSUPPORTED_SOURCE=31 SPOTIFY=32 XMLY=33 …`
**没有酷狗这一档**。所以自装的酷狗在原车卡片上只能落到「未知频道」——不是权限问题，是白名单问题。
对策：我们自己 new 一个 `VDMediaInfo`，`mediaType` 填 `ONLINE_MUSIC(14)`，用
`VDEventMedia.createEvent(393218, info)` + `VDBus.set()` 推上去，见 `源码/src/.../Vd.publishMedia()`。

事件号统计见 `证据-媒体总线事件.txt`；桌面反编译见 `反编译/t1h.dump`、`反编译/launcher-classes*.dex.dump`。

## 4. 读「正在放什么歌」用系统标准接口

`NotificationListenerService` + `MediaSessionManager.getActiveSessions()`，一条 adb 命令授权、重启不失效：

```
adb shell cmd notification allow_listener com.ahui.clustercast/.MusicListener
```

**这里踩过一个坑**：车机上 `com.bytedance.byteautoservice3` 这个常驻会话一直上报
`STATE_PLAYING` 但 `metadata: null`，按播放状态先挑就会选中它，真正在放歌的酷狗反而被跳过，
页面显示成「没有正在播放的音乐」。证据见 `media_session.txt`：

```
Kugou_Media   ... state={state=3, position=197820}  metadata: size=9, description=曹操, null, null
ByteMedia     ... state={state=1, position=0}       metadata: null
```

已改成只在「带歌名」的会话里挑正在播放的那个（`MusicListener.active()`）。

## 5. 投屏本身

`ActivityOptions.makeBasic().setLaunchDisplayId(2)` + `startActivity`，零权限可用。
`FLAG_ACTIVITY_MULTIPLE_TASK` 对 launchMode>standard 的窗口无效，所以 singleTask 的应用
（酷狗、腾讯地图）没法在主屏和仪表屏同时存在两份实例——这也是走「仪表只放我们自己的极简页」
而不是「把应用搬过去」的原因之一。

## 6. 还没定论的一件事（下次连车第一件事）

**写入 cmdId 232 = 4 之后，仪表到底切没切到极简模式。**

v3.2.1 及之前的日志里那句「仪表已切到极简模式（原=3）」是假的——`VDBus.set()` 返回 void，
代码里只要没抛异常就当成成功了，从没回读。你反馈仪表还停在导航模式，正好和这个漏洞对上。

v3.2.2 已经改成：写入后 sleep 250ms 再 `getTheme()` 回读，按回读结果决定日志措辞，
没切过去会直接写「写极简模式没生效，仪表还停在导航模式」。

下次连车，同时开这条日志就能一次定性：

```
adb logcat -s ClusterCast:V ClusterCast.Vd:V VDS-CarInfo-CarInfoService:V VDConnector:V
```

- 如果能看到 `VDS-CarInfo-CarInfoService ... onSet ... cmdId = 232 values = [4]` 且回读是 4
  → 总线这条路通了，问题在别处（比如极简模式只是背景，投屏通道是另一个概念）。
- 如果**没有** onSet 这行 → 我们的 `set` 根本没到达服务端，得换 `CarInfoProxy` 那条注册路径
  （`原车jar/vdbus_extra.jar` 里的 `com.desaysv.ivi.extra.project.carinfo.proxy.CarInfoProxy`，
  它是公开类，可以直接反射调用，和 SystemUI 走完全同一条代码）。

## 怎么编译

```
powershell -ExecutionPolicy Bypass -File 源码\build_clustercast.ps1
```

需要 `~/AndroidSDK`（build-tools 34.0.0 + platforms/android-34）和一个 JDK，脚本顶部有路径变量。
两个已知的坑写进了脚本注释：
1. aapt2/javac 在含中文的路径下会失败，所以源码先同步到 `%TEMP%\ccbuild3` 再构建，产物拷回；
2. d8 编不了「捕获 this 的匿名内部类」，本项目里所有回调一律用 lambda 或
   `static` 嵌套类 + `WeakReference`（见 `CastService.Refresh` / `MirrorTick` / `ClusterActivity.Tick`）。

装包（这台 ROM 的 `adb install` 被策略挡了：`SecurityException: Restriction prevents installing`），
只能走 MT 管理器：

```
adb push ClusterCast-v3.apk /sdcard/Download/
adb shell am start -n bin.mt.plus/.OpenFileActivity \
  -d file:///sdcard/Download/ClusterCast-v3.apk \
  -t application/vnd.android.package-archive
```
