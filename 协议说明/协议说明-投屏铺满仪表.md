# 协议说明 —— 投屏铺满仪表（QNX 合成 + CabinLAN 隧道）

> 全部取自实机：2026-09-21 03:07 抓的 psmap 生命周期 logcat、`/system/framework/vdbus.jar` 反编译、
> 以及原车高德 `com.desaysv.jetour.t1n.psmap` / SVSystemUI 的 dexdump。推断的地方都标了"未验证"。

## 0. 一句话结论

面板不是 Android 合成的。`ro.product.device=msmnile_gvmq`，Android 是 QNX 虚拟化里的 guest，
display 2（`local:2`，1920x720，invalid EDID，layerStack 2）是一块虚拟 HDMI 输出，
**由 QNX 侧的仪表程序把它塞进一个矩形里显示**，四周再画自己的 HUD。
所以在 Android 里怎么置顶、铺满、改 Z 序都没用——黑边框就是那个矩形的边。

## 1. 让仪表"让位"给投屏：CabinLAN 0x1004

原车高德（psmap）启动那一下，实机抓到三条：

```
CarDashboardBusiness: showMapViewToDashboard data=
  {"DisplayCluster":"true","NaviFrontDeskStatus":"true","Perspective":0,
   "PerspectiveResult":"false","RequestDisplayNaviArea":"false"}
vdev.service.cabinlan|vehiclebus(592): CabinLANVDS::mRemoteCommon->setMessage,
  MsgType = 0x1004, SubType = 0x2, Content = {上面那串}
vdev.service.cabinlan|vehiclebus(592): ... writeMessage! result = 0
```

完整时序（03:07:56.772 → 03:08:00.371）：

| 顺序 | MsgType | SubType | Content |
| --- | --- | --- | --- |
| 1 | `0x1004` | `0x9` | `{"NaviDisplayLoading":1}` |
| 2 | `0x1004` | `0x2` | `{"DisplayCluster":"true","NaviFrontDeskStatus":"true","Perspective":0,"PerspectiveResult":"false","RequestDisplayNaviArea":"false"}` |
| 3 | `0x1004` | `0x9` | `{"NaviDisplayLoading":0}` |

**关键性质：这条状态是"锁存"的。** 高德被禁掉之后 QNX 不会自己复位，仪表就把 display 2 的流
一直显示在那块矩形里——这就是"先解禁原车高德、再禁用，投屏才会透出来"的底层原因。

## 2. Android 侧怎么发出去（两条路，都不需要特权）

### 2.1 走 CAR_LAN 的带类型的 bean（SystemUI / 高德用的就是这条）

`VDBus.getDefault().set(VDEvent)`，事件号落在 CAR_LAN 段 `720896 ~ 786431`：

| eventId | 常量 | payload（Bundle key `"data"`，Parcelable） |
| --- | --- | --- |
| `721699` | `NAVIGATION_DISPLAY_TO_CLUSTER` | `VDNaviDisplayCluster{String DisplayCluster, String NaviFrontDeskStatus, int Perspective, String PerspectiveResult, String RequestDisplayNaviArea}` |
| `721702` | `NAVIGATION_DISPLAY_AREA` | `VDNaviDisplayArea{int NaviDisplayArea, String NaviDisplayAreaResult}` |
| `721705` | `NAVIGATION_AREA_DISPLAY_REQUEST` | `VDNaviAreaDisplay{int RequestNaviAreaDisplay}` |

布尔字段是**字符串** `"true"` / `"false"`，不是 boolean。

`NaviDisplayArea` 取值（`VDValueCarLan$NaviDisplayArea`）：
`0=CLOSE_CAST_SCREEN 1=MIDDLE_FIRST_THEME 2=LEFT_FIRST_THEME 3=SECOND_THEME 4=THIRD_THEME`
—— 高德把 AR 那档写死成 2、导航那档写死成 1（`AR_DISPLAY_AREA` / `NAVI_DISPLAY_AREA` 两个 JSON 常量）。

### 2.2 走 CABIN_LAN 的裸 JSON 隧道（没有 bean 的那几条只能走这里）

```
eventId = 1114113   // VDEventCabinLan.CABIN_LAN_MSG_COMMON
bean    = VDCLCommonMessage{ setMsgType(int) / setSubtype(int) / setMessage(String json) }
```

Bundle 键前缀 `CabinLanMessageData_`（`_MsgType` / `_SubType` / `_Content`）。
VDS 服务收到后原样转成上面表格里的 `MsgType/SubType/Content`。

### 2.3 权限结论（实测，别再猜）

```
ClusterCast.Vd: connect carInfo=true media=true carLan=true cabinLan=true
```

`com.ahui.clustercast` 是 uid 10018 的 `untrusted_app`，**CAR_LAN 和 CABIN_LAN 都绑得上**：
`SVVDSCarLan.service.CarLanService` / `SVVDSCarInfo` 都是 `exported=true` 且**没有** `android:permission`。
CABIN_LAN 虽然是 `*_SYSTEM_SERVICE=true`（走 ServiceManager 查 `CabinLanService`，宿主 pid 592 root），
SELinux 也没拦。所以整套铺满方案零特权，不需要 root / Shizuku / 无障碍。

## 3. 还没定的那一件事

矩形到底是**谁**、**按什么**定的。已知事实：

- 同一份 display 2 内容（1920x720 满幅），夜间档透出大、白天档透出小 → 矩形跟着仪表主题/昼夜走。
- 高德活着的时候它占的是全屏 overlay（window type 2038），所以它自己那套矩形逻辑我们看不到。

`4.2.1` 的投屏页底部加了「仪表铺满试验」四排按钮，点一次拍一张面板即可定位：
布局档 0~4、申请/交还显示区、让出/占住仪表页、复刻高德三连、释放仪表、加载态探测。
日志里会写明 `已发出（CAR_LAN 已绑 / CABIN_LAN 已绑）`，`已发出` 只代表发出去了，
**生效与否只认面板照片**，QNX 不回话。
