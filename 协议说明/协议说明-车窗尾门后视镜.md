## 0. 调用形态

上层封装（原厂应用用的是这套，比裸 VDBus 省事）：

`CarInfoModel` 里 `sendCarSettingValue / sendCarSettingValues / sendAndResponseCarSetting`
全部硬编码 **moduleId = 327681（0x50001）**，只有天窗走 **327696（0x50010）**，空调走 **327690（0x5000A）**。

已确认在用的 moduleId 清单：**327681**（车身控制 / 座椅 / 方向盘 / 仪表模式）、**327684**（档位等车辆状态，见 §6）、
**327688**、**327690**（空调）、**327691**、**327696**（天窗）—— 都是同一条 CAR_INFO 总线，
换个 eventId 数字就行，`VDEvent` 的 Bundle key 仍是 `CMD_ID` / `VALUE`。

裸总线（我们 `Vd.java` 用的那条）等价于：
`VDEvent(327681, Bundle{putInt("CMD_ID",cmdId); putIntArray("VALUE",values)})` → `VDBus.set()` / `getOnce()`。

**抓包钩子（比 onSet 更好用）**：`CarInfoModel` 每次下发都打
`I/CarInfoModel: 下发指令，moduleId=327681,requestCmdId=162,value=3`，
多参数版是 `下发多参数指令，...`。下一轮抓尾门/后视镜时直接
`adb logcat -s CarInfoModel VDS-CarInfo-CarInfoService` 就够，不用大海捞针。

| 1 | 关闭（全关） | "关闭全部车窗" → 4×`[1]` ✅ |

### 关键结论：**没有 60% 档**

原厂只认两档百分比，而且两档都落到同一个值 3：

- 打开方向：`开启程度调节仅支持20%`（`parseInt(x)==20 || ==100` 才继续，否则直接话术拒绝）
- 关闭方向：`很抱歉，车窗关闭百分比仅支持80%哦`（`parseInt(x)==80 || ==100`）
- 关到 80% 的分支体里发的就是 **值 3**（和"开 20%"完全同一条命令，同一个物理开度）

所以我们要的「20% / 60% / 全开 / 全关」四挡里，**60% 在原车总线上不存在**。
可选处理：只做 透气(3) / 全开(2) / 全关(1) 三挡；或者"60%"按钮降级成"透气"并提示。
（不要指望发个 60 过去能线性走——162~165 的取值空间是枚举，不是百分比。）

### 原车的软件前置锁（`WindowController`）

发命令前先判三个条件，任一命中就只回话术不下发：

1. `isWinLock()` → 「抱歉，你需要先解除车窗锁哦」
2. `isWearCar()` 洗车模式 → 「洗车模式暂不支持调节车窗哦」
3. `isParkAC()` 驻车空调 → 「驻车空调开启时，语音不支持打开车窗哦」

**行车中禁止开窗不在这个 APK 里**，即由 MCU 侧执行 —— 我们绕过原车 UI 直接发总线时
会不会被 MCU 挡，必须上车实测（这是那张"行驶中禁止打开"需求的唯一未知点）。

### 7.0 ⚠ `keyGear` 不是排挡，别拿它当档位

2026-09-19 21:28 复核：整段 logcat 缓冲里 `TBoxCommonManager: keyGear = 2` 出现 **357 次、只有 `2` 一个值**，
而同一时刻真实的排挡在来回跳——

| 信号源 | 取值分布 | 频率 | 能不能当档位用 |
|---|---|---|---|
| `TBoxCommonManager keyGear` | 只有 `2`（357 次） | 1Hz 定周期 | **不能**，恒定值，大概率是点火开关档位（ACC/ON），撞见 2 = R 纯属巧合 |
| `CheryPlatformCarInfoManager mGearPosition` | `1`/`2`/`3` | 变化时才打 | 可以（间接证据） |
| `Account-DeviceEnvDatasourceImpl onGearStateChanged` | `N`/`P`/`R` | 变化时才打 | 可以 |
| **VDBus event 327684 / cmdId 26** | 1=P 2=R 3=N 4=D | 变化时一小串 | **权威**，见 §6 |

上面那条时间线里 `keyGear = 2` 排在第一行，是因为它 1Hz 一直在打、恰好最早出现，

**教训**：定周期日志和事件驱动日志混在一起看时，先统计某个字段在整个缓冲里的**取值分布**，
只有一个值的直接排除，不要拿它当状态量。

### 7.3 硬结论：**倒车/360 画面拿不到帧，不能嵌进我们自己的框里**

挂 R 的整个窗口内：

- `dumpsys media.camera` → `No active camera device session instance`，设备 **4/5/6/7 全部 closed**
  （HAL 枚举到 4 个 camera，就是前/左/右/后四路），Android 侧一次都没 open；
- `dumpsys window windows` 26 个窗口里**没有任何 rvc / avm / camera 窗口**；
- `screencap` 两张（display 1、display 2）里都看不到倒车画面，foreground 还是我们的 `MainActivity`。

**360 是谁画的——已查明（20:46~20:56 追加实测）**：桌面应用列表里那个「全景影像」就是
`com.desaysv.carmodel`（`/product/app/KanziCarModel/KanziCarModel.apk`，Rightware Kanzi 渲染），
清单里只有一个 `com.rightware.kanzi.carmodel.MyActivity`（**只有 MAIN、没有 LAUNCHER category**）
和一个 **exported 前台服务** `CarModelService`（`isForeground=true`，常驻）。

用 adb 直接拉起它：

```
am start -n com.desaysv.carmodel/com.rightware.kanzi.carmodel.MyActivity
→ mResumedActivity 确实变成它；Android 侧画面 = 全黑 + 一个「测试」按钮（点一下 finish 回桌面）
→ dumpsys SurfaceFlinger --list 里出现
     "SurfaceView - com.desaysv.carmodel/...MyActivity" 和 "Background for -SurfaceView - ..."
→ 但 screencap 抓不到任何 Kanzi 内容；W/Kanzi(2246) 一直在刷渲染日志
→ 用户口述：P 档下这个页面就是黑的，没有 360 画面
```

配套证据链：

- Kanzi 取流**不走 CameraService**：`dumpsys package com.desaysv.carmodel` 权限里**没有 CAMERA**，
  只有 `SYSTEM_ALERT_WINDOW / WAKE_LOCK / READ|WRITE_EXTERNAL_STORAGE`；
  底层节点是 `/dev/video51`~`/dev/video58`，`crw-rw---- system:camera` → **普通应用（uid 10018）打不开**。
- 挂 R 时那个 360+后视画面**没有对应的 Android 窗口**，所以它不是 `MyActivity`，
  是 Kanzi 服务/硬件通路直接出的一个独立显示平面，Android 的合成结果里根本不存在它。
- 环视状态在总线上的 key 叫 **`avm_floating`**（`SettingImplPlatform: onVDNotify: avm_floating=0` /
  `getAvmFloating` / `SpiModel.isAVMIsFull` / `AVMManager(1033).getAVMStatus`），事件就是 **786835**。
- 桌面 launcher（pid 1234）里有 **`CarModelViewModel.setPreseAngle(int)`**，"车模预设视角"有软件入口。
- 顺带钉死：cmdId **71 = 日期时间**，系统每秒 `onSet` 一次 `[年,月,日,时,分,秒]`，别当状态量。

→ 倒车视频是硬件/独立显示平面，**不经过 Android 的合成结果**。
所以：
1. 我们的"倒车"页只能做**信号感知 + 主动让位**（收到 VIDEO_SIGNAL=1 / RVC_STATUS=2 就把自己的层隐藏、
   退出时再恢复），**不能**复刻或叠加原车倒车画面；
2. ~~自己取流判死~~ → **§9 推翻：四路摄像头可以正常取流**，"左侧 3 个摄像头框"重新变为可做；
3. R 档会抢音频焦点（`carAudioType=rvc, sourceId=43`），我们投屏/音乐卡片在 R 期间要预期被 duck。

android.sensor.info.activeArraySize = [0 0 1280 800]

### 9.1 cameraId ↔ 页面标签（从 `T1JCameraActivity.onCameraAvailable` 反编译钉死）

| cameraId | 工程模式标签 | 方位 |

| 1 | OMS | 乘员监测（黑） |

| **7** | AVM4 | **后**（画面是车后街道） |

（3 号在这台车上不存在，`Number of camera devices: 4` 但 id 是 4~7。）

**左右怎么钉死的（三条独立证据一致，第 3 条是决定性的）**：

1. 人站在车边实测哪格亮（用户 2026-09-19 21:15 报告，先说反了一次、随后更正）。
2. 几何互证：`android.lens.facing` 四路都报 BACK，元数据不可用，只能用场景对。
   AVM1（前视）里砖楼在画面右 → 前视"画面右 = 车身右"；
   AVM4（后视）里同一栋砖楼在画面左 → 后视"画面右 = 车身左"，两侧互证 **砖楼在车身右侧**。
   AVM2 拍到的正是那堵砖楼，AVM3 拍到的正是那排店面。
3. **遮挡差分（单变量，决定性）**：用户用手遮住**驾驶侧**后视镜下方那颗，同时连拍 40 张，
   逐格算平均亮度，**只有 id 6 那一格动了**，其余三格 40 张里波动 < 0.5：

   | 帧 | id4 | id5 | **id6** | id7 |
   |---|---|---|---|---|
   | c12 遮前 | 53.6 | 40.0 | **14.7** | 55.4 |
   | c14 全遮 | 53.3 | 39.9 | **31.6** | 55.4 |
   | c16 松手 | 53.5 | 40.2 | **15.5** | 55.5 |

   → **id 6 = 左（驾驶侧）**，按排除法 **id 5 = 右（副驾侧）**。

   **坑**：遮住后是**变亮**不是变黑（手离镜头近、被环境光照着，比夜晚空场景亮一倍）。
   判据要写"哪一格发生了大幅相对变化"，不要写"哪一格变黑"。

### 9.2 用之前要处理的事

1. ~~5/6 谁是左谁是右~~ → 已定：**5=右、6=左**（见 §9.1）。
2. **和原车硬件倒车通路的冲突**——**已排除 CameraService 层，风险下沉到 V4L2/ISP 层**：

   2026-09-19 21:29:22→21:30:53 实机挂 R **91 秒**（`rvc status=1` + `mGearPosition=2` + `onGearStateChanged: R` 三处对齐），
   采样窗口 21:29:32→21:30:12 内每 1.2 秒查一次 `dumpsys media.camera`，**active client 数恒为 0（16/16 次）**。

   → 原车倒车影像**完全不注册 CameraService**，它是绕开 CameraService 直接开 V4L2 节点
   （`/dev/video51~58`，`system:camera 0660`）的通路。所以：
   - 我们 `open("7")` **不会**因为"被原车占着"而报 `in use`；
   - 我们也**不会**在 CameraService 层把原车画面挤掉。

   **但冲突仍可能在更底层**：CameraService 给 id 7 供帧时，HAL 大概率开的是同一个物理节点，
   ISP/CSI 独占会在"我们 open 成功却收不到帧"或"原车画面花屏/黑屏"上暴露出来。

   **② 的判据（不要只看 `onOpened`）**：
   | 观察项 | 通过 | 不通过 |
   |---|---|---|
   | 我们 `open("7")` | 回调 `onOpened` | 报 `ERROR_IN_USE` / `ERROR_CAMERA_DISABLED` |
   | **帧计数**（`Frames produced` / `onImageAvailable`） | **持续上涨** | open 成功但计数不动 → 底层被独占，**判失败** |
   | 你肉眼看原车 360 | 正常 | 黑屏 / 花屏 / 延迟出画 → **R 档自动开摄像头这条直接砍** |
   | 退 R 后 | 我们帧恢复、原车 360 正常 | 有一边起不来 |

   **② 实测结果：通过（2026-09-19 21:44~21:46）**。我们自己装的探针 `com.ahui.camprobe`
   （普通应用签名，pid 18753，CAMERA 靠运行时弹窗给的）在 21:44:41 把 **4/5/6/7 四路全部 open 成功并进入
   `STREAMING`**，`dumpsys media.camera` 显示 `(Cost: 10, PID: 18753, Client Package Name: com.ahui.camprobe,
   Conflicting Client Devices: {})` × 4，`Dims: 1280 x 800, format 0x11`。
   然后挂 R：**21:45:37.520 `mGearPosition=2` → 21:46:21.998 `mGearPosition=1`，R 持续 44.5 秒**。

   对这 44.5 秒做逐帧差分（`framerate.awk`，离线跑落盘的 `adb logcat -v time`，边跑边查会漏）：

   | cameraId | R 窗口内采样数 | 每次采样帧增量 | 异常状态行 |
   |---|---|---|---|
   | id4 前 | 44 | **最小 25 / 最大 25** | 无 |
   | id5 右 | 44 | **最小 25 / 最大 25** | 无 |
   | id6 左 | 44 | **最小 25 / 最大 25** | 无 |
   | id7 后 | 44 | **最小 25 / 最大 25** | 无 |

   全程 176 个采样点**一次都没掉过速**（唯一的 0 增量是 21:44:40~41 刚 `onOpened`、还没开始出图的种子行）；
   没有 `onDisconnected` / `onError`；R 窗口内 `dumpsys media.camera` 侧没有任何 `conflict` / `in use` /
   `max_cameras` 日志。用户肉眼看原车 360：**"R 档画面正常，没有黑屏或花屏"**。退 R 回 P 后继续出图
   （21:46:58 左 id6 `STREAMING frames=3428`，分析时刻四路已到 7716~7733 帧）。

   **结论**：
   - 我们四路同开 **不会** 把原车倒车/360 画面挤黑 —— 上面"ISP/CSI 独占"的担心，在**行为层面**已被实测否掉；
     （准确说是否掉了"会互相打黑"这个结论，而不是证明了两条通路共用同一个物理节点。
     原车仍可能走的是另一组 `/dev/videoNN`，只是互不影响。）
   - 原车 RVC 拉起 **不会** 断我们的流 —— 反向也没事。
   - 所以 **「挂 R 自动开我们自己的摄像头画面」这条能力保留，不用砍**。
   - 仍然要按 §9.2 第 4 条写降级：拿不到帧就显示黑框，别把行车界面卡死。
3. 四路并发 Cost 各 10（共 40），远低于常规 1000 预算，**四路同开没问题**（工程模式已经这么干了）。
4. **同一时刻只能有一个客户端 open 同一颗**：`Conflicting Client Devices: {}` 说明这 4 颗互不冲突，
   但工程模式占着的时候我们 open 同一 id 会失败。所以**我们自己的页面不能和工程模式同时跑**，
   而且以后如果原车 AVM 应用改成 Android 侧取流，会和我们抢——落地时要按"拿不到就降级显示黑框"写。
5. ~~**我们自己的应用能不能拿到 CAMERA 权限**~~ → **能，运行时弹窗就够了**（2026-09-19 21:44 实测）。
   `com.ahui.camprobe` 是普通签名 + 手动安装的包，弹窗点允许后 `dumpsys package` 显示
   `android.permission.CAMERA: granted=true, flags=[USER_SET]`，四路 camera 全部 open 成功。
   **不需要 root、不需要 `pm grant`、不需要平台签名**，符合本项目"装一次长期可用"的硬约束。
   - 坑：`requestPermissions()` 是异步的，`onSurfaceTextureAvailable` 会先触发 `open()`，
     第一次必然 `SecurityException: cannot open camera "4" without camera permission`。
     必须在 `open()` 前 `checkSelfPermission` 挡一下并在 `onRequestPermissionsResult` 里重试；
     这条修复已进 `源码/camprobe`（**注意：修完还没重新打包，设备上装的仍是 21:42 那个有竞态的版本**，
     因为权限已经永久记住了所以表现正常）。
   - 另一条坑：`adb install -r -g` / `adb install -r` / `pm install` 在这台 ROM 上全部
     `SecurityException: Restriction prevents installing`（门禁在 shell uid 上），
     装包只能走"推到 `/sdcard/Download/` + MT Manager `OpenFileActivity`"，见 `README.md`。
6. **工程模式那页拉不起来**：`am start -n com.desaysv.engmode/.ui.T1JCameraActivity` 报
   `SecurityException: not exported from uid 1000`（activity 未导出，连 adb shell 都进不去），
   只能手点进去。所以它只能当"取证工具"，不能当集成路径。
